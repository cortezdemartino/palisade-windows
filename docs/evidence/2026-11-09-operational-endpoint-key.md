## Restart gap and compatible correction

The service's `enrollEndpoint` always creates a new endpoint ID and challenge and
revokes older native grants for that publisher/device. Its `proveEndpoint` verifies
the current tuple but does not itself create a new enrollment. The web controller
already follows enroll.key, authenticated POST endpoint, enroll.prove and POST proof.

Previously native endpoint signing used the persistent DPAPI key. A new native
process could confirm an old endpoint/challenge again, construct a new empty gate,
and authenticate leases with the same key. Fresh local confirmation alone did not
prove a fresh service grant after restart.

The native API now separates:

- `Identity`: the preserved current-user DPAPI installation identity, unchanged
  path/format/entropy and fail-closed corruption handling. It exposes no operational
  endpoint signing methods.
- `EndpointIdentity`: a distinct memory-only operational signer generated by Windows
  CSPRNG for one native authority launch. Construction requires a validated installation
  identity, retains its public local reference and never loads or falls back to its
  private signing key. The temporary random seed is zeroized.

Enrollment, EnrolledIdentity, Runtime and LeasePoller require EndpointIdentity.
Enrollment proof, grant acknowledgement and endpoint-lease authentication use that
same operational signer. A new launch key cannot authenticate an old endpoint ID
against the service's stored old public key. A new gate has no covering lease and
the page cannot supply one; the independent native endpoint-lease path must succeed
before any privileged admission.

The native confirmation now distinguishes the installation reference from the
current endpoint public key. This is not a change to updater verification keys,
service issuer trust anchors, Matrix credentials, installation paths or Electron
session storage. No companion source or protocol field changed.

## Integration requirements still open

The real coordinator must create and retain exactly one operational identity per
authority launch, not per page request, grant or peer. Replacement of that authority
owner discards the old signer and requires fresh canonical enrollment. Never expose
a generic signer, accept page/cached leases or a page-provided endpoint-proven flag,
or substitute the persisted key on failure.

Future ICE/transport/relay statements must use the same operational signer after
their own exact native authorization checks. Those signing paths are not implemented
by this key-lifetime component.

Retain ended-session/acquisition tombstones within a launch. Replacing a gate with
a new minimum-generation-zero gate for the same session must not revive authority.
Ephemeral keys address cross-launch replay, not that separate in-launch registry gap.
Initial mixed capability generations can be legitimate; replacement-cohort rules
must not reject them solely for being different.
